# TraceLock Codebase Analysis

A physical access control API built with Go, Chi, PostgreSQL, JWT auth, hash-chain audit logs, WebSocket live feed, and biometric device authentication. Solid project — here's the full breakdown.

---

## Overall Impressions

**What's done well:**
- Clean layered architecture (handler → service → repository) with proper separation of concerns
- Repository interfaces with mock-based unit tests — testability is a first-class concern
- Hash-chain audit trail — creative tamper-detection mechanism
- Auto-exit logic across zones is well thought through
- Graceful shutdown with signal handling
- Good error sentinel pattern with `errors.Is()` throughout
- Rate limiting on auth routes
- Account lockout after failed login attempts
- WebSocket real-time zone occupancy broadcasting

## 🔴 Critical Bugs

### 1. Infinite Recursion in `UpdateRole` — **Will crash the server**

> [!CAUTION]
> [user_service.go:67](file:///home/amonoff/Projects/tracelock/internal/auth/user_service.go#L63-L68) calls **itself** instead of `s.auth.UpdateRole()`. This is a stack overflow that will crash the process on the first admin role-update call.

```go
// BUG: recursive call — this calls itself, not the repo
func (s *UserService) UpdateRole(userID int, role string) error {
    if role != "admin" && role != "user" {
        return ErrInvalidRole
    }
    return s.UpdateRole(userID, role) // ← should be s.auth.UpdateRole(...)
}
```

### 2. `logDeniedEvent` discards the `reason` parameter

[access_service.go:223-224](file:///home/amonoff/Projects/tracelock/internal/access/access_service.go#L223-L224) — The `reason` parameter is accepted but immediately silenced with `_ = reason`. This means the `status` field in the event is always `"denied"` with no distinction between `no_access`, `zone_full`, `already_in_zone`, or `not_in_zone`. You lose forensic value.

```go
func (s *ZoneService) logDeniedEvent(..., reason string, ...) {
    _ = reason  // ← why accept it then?
```

**Fix:** Store `reason` in the event — either as a separate field or by appending it to the status: `"denied:zone_full"`.

### 3. Hash-chain race condition under concurrent access

The `HandleZoneEvent` function does `GetLastHash` → `GenerateHash` → `CreateEvent` as three separate operations with no transaction or locking. Under concurrent entry to the same zone, two goroutines can read the same `previousHash` and both write events pointing to it, forking the chain. This makes `VerifyChain` silently unreliable under load.

**Fix:** Wrap the hash-fetch + event-insert in a serializable transaction, or use `SELECT ... FOR UPDATE` on the last event row.

## 🟠 Security Weaknesses

### 4. JWT Secret is too weak

[.env:7](file:///home/amonoff/Projects/tracelock/.env#L7) — `JWT_SECRET=amonofftrace` is 12 characters and dictionary-guessable. HMAC-SHA256 requires a secret with at least 256 bits of entropy. Use `openssl rand -base64 32` to generate a proper one.

### 5. Biometric auth endpoint has no authentication at all

[router.go:36](file:///home/amonoff/Projects/tracelock/internal/httpdir/router.go#L36) — `POST /devices/authenticate` is outside the JWT middleware group. Anyone who knows a device ID and credential hash can trigger zone entry. This endpoint needs at minimum:
- Device API key authentication, or
- IP allowlisting, or
- mTLS

### 6. `/bootstrap` endpoint is permanently open

[router.go:32](file:///home/amonoff/Projects/tracelock/internal/httpdir/router.go#L32) — While `BootStrapAdmin` checks if an admin already exists, it still exposes an unauthenticated POST endpoint that can be probed indefinitely. After the first admin is created, this should be disabled or rate-limited.

### 7. Refresh token stored in plaintext in the database

The refresh token is stored as-is in the `refresh_tokens` table. If the database is compromised, every refresh token is immediately usable. **Hash the refresh token** (SHA-256) before storing; compare hashes on lookup.

### 8. WebSocket and Occupancy endpoints are unauthenticated

[router.go:39](file:///home/amonoff/Projects/tracelock/internal/httpdir/router.go#L39) and [router.go:42](file:///home/amonoff/Projects/tracelock/internal/httpdir/router.go#L42) — `GET /ws/zones` and `GET /zones/occupancy` are public. Anyone can view real-time occupancy data including user names and emails. This leaks PII.

### 9. No CORS middleware

The `AllowedOrigin` config exists and the WebSocket upgrader uses it, but there's no CORS middleware on the HTTP routes. The frontend will hit CORS preflight errors. You'll need `chi/cors` or a custom middleware.

### 10. No password hashing for biometric credentials

Biometric credential hashes are stored and compared as literal strings in `biometric_credentials.credential_hash`. If the client sends a raw biometric template, it should be hashed server-side before storage. The current flow assumes the client pre-hashes, which is fine if documented — but there's no validation that the hash looks reasonable (length, format).

## 🟡 Code Quality & Design Issues

### 11. `DeviceService` and `CredentialService` are pass-through layers

Both services do nothing except forward calls to their repositories. They add no validation, business logic, or error enrichment. Either:
- Add validation (e.g., serial format, credential hash length checks), or
- Remove the service layer and inject the repo directly

### 12. `DeviceService` depends on concrete `*DeviceRepo` instead of `DeviceRepository` interface

[device_service.go:6](file:///home/amonoff/Projects/tracelock/internal/access/device_service.go#L5-L6) — You defined `DeviceRepository` and `CredentialRepository` interfaces but `DeviceService` and `CredentialService` depend on the concrete struct. This defeats the purpose of the interface — you can't mock them in tests.

```go
// Currently:
type DeviceService struct {
    repo *DeviceRepo  // ← concrete
}

// Should be:
type DeviceService struct {
    repo DeviceRepository  // ← interface
}
```

Same issue with `CredentialService`.

### 13. `UserAuth` and `UserService` don't use interfaces

The `auth` package has no repository interface at all. `UserAuth` holds `*sql.DB` directly. `UserService` holds `*UserAuth`. Neither is testable without a live database. Extract a `UserRepository` interface like you did for zones.

### 14. `BiometricService` depends on concrete `*CredentialRepo` and `*DeviceRepo`

[biometric_service.go:18-20](file:///home/amonoff/Projects/tracelock/internal/access/biometric_service.go#L18-L20) — Same as #12. Should use the interfaces.

### 15. `rows.Err()` is never checked after scanning

Every `for rows.Next()` loop in the repos (e.g., `ListUsers`, `ListZones`, `ListZoneDevices`) exits the loop without checking `rows.Err()`. If the database connection drops mid-scan, you silently return partial results.

```go
// Add after every for rows.Next() loop:
if err := rows.Err(); err != nil {
    return nil, fmt.Errorf("iterating rows: %w", err)
}
```

### 16. `GetRefreshToken` doesn't return the associated `user_id`

[user_auth.go:171](file:///home/amonoff/Projects/tracelock/internal/auth/user_auth.go#L171) — `GetRefreshToken` validates the token but returns only an `error`. Then `RefreshAccessToken` in the service makes a **second** query (`GetUserIDFromRefreshToken`) to get the user ID. This is two round trips for one logical operation. Return the `user_id` from the first query.

### 17. Error comparisons mix `errors.Is()` and `==`

[user_service.go:26](file:///home/amonoff/Projects/tracelock/internal/auth/user_service.go#L26) uses `err == ErrInvalidCredentials` instead of `errors.Is(err, ErrInvalidCredentials)`. This will break if the error is ever wrapped. Be consistent — use `errors.Is()` everywhere.

### 18. Test routes left in router

[router.go:53-60](file:///home/amonoff/Projects/tracelock/internal/httpdir/router.go#L53-L60) — `/protected` and `/testjwt` are debug routes. Remove before deploying.

## 🔵 Database & Schema Issues

### 19. No indexes on high-query columns

The `access_events` table will grow fast and has no indexes beyond the primary key. These queries will become slow:
```sql
-- These need indexes:
WHERE zone_id = $1 ORDER BY timestamp DESC  -- ListZoneEvents
WHERE user_id = $1 ORDER BY timestamp DESC  -- ListUserEvents
WHERE zone_id = $1 ORDER BY timestamp ASC   -- VerifyChain
```

**Add a migration:**
```sql
CREATE INDEX idx_access_events_zone_ts ON access_events(zone_id, timestamp DESC);
CREATE INDEX idx_access_events_user_ts ON access_events(user_id, timestamp DESC);
CREATE INDEX idx_refresh_tokens_token ON refresh_tokens(token);  -- if not already UNIQUE
```

### 20. No `ON DELETE CASCADE` on `access_events` foreign keys

[000004 migration](file:///home/amonoff/Projects/tracelock/migrations/000004_create_access_events_table.up.sql#L3-L5) — `user_id` and `zone_id` reference users/zones but have no cascade behavior. If you delete a user or zone, any events referencing them will cause FK violations. You probably want `ON DELETE SET NULL` (preserve the audit trail) or `ON DELETE RESTRICT` (prevent deletion if events exist).

### 21. `active_sessions` allows user in multiple zones simultaneously

The primary key is `(user_id, zone_id)`, meaning a user can have sessions in zone 1, zone 2, and zone 3 at the same time. Your application code prevents this via auto-exit, but the database doesn't enforce it. If a bug or direct SQL bypasses the app, the invariant breaks.

**Consider:** A `UNIQUE(user_id)` constraint on `active_sessions` to enforce single-zone occupancy at the database level.

### 22. Migration path is relative — fragile in production

[migrations.go:21](file:///home/amonoff/Projects/tracelock/internal/db/migrations.go#L21) — `file://migrations` is relative to the working directory. This will break if the binary is run from a different directory (e.g., systemd, Docker). Use an embedded filesystem (`embed.FS`) or make the path configurable.

## 🟢 Minor Improvements

### 23. No DB connection pool configuration

[db.go](file:///home/amonoff/Projects/tracelock/internal/db/db.go) — `sql.Open` creates a pool but uses Go's defaults (unlimited connections, no idle timeout). For production, set:
```go
db.SetMaxOpenConns(25)
db.SetMaxIdleConns(5)
db.SetConnMaxLifetime(5 * time.Minute)
```

### 24. No HTTP read/write timeouts on the server

[main.go:70-73](file:///home/amonoff/Projects/tracelock/cmd/api/main.go#L70-L73) — `http.Server` has no `ReadTimeout`, `WriteTimeout`, or `IdleTimeout`. This makes the server vulnerable to slowloris attacks.

```go
srv := &http.Server{
    Addr:         ":" + cfg.Port,
    Handler:      handler,
    ReadTimeout:  10 * time.Second,
    WriteTimeout: 30 * time.Second,
    IdleTimeout:  60 * time.Second,
}
```

### 25. Token cleanup goroutine starts with a 24h sleep

[main.go:40](file:///home/amonoff/Projects/tracelock/cmd/api/main.go#L39-L46) — The cleanup goroutine sleeps for 24 hours before doing its first run. Expired tokens from before startup won't be cleaned until a full day later. Run once immediately, then loop:
```go
go func() {
    for {
        if err := userService.DeleteExpiredTokens(); err != nil {
            log.Printf("token cleanup failed: %v", err)
        }
        time.Sleep(24 * time.Hour)
    }
}()
```

### 26. `WriteError` after `WriteJSON` header is already sent

[response.go:18-20](file:///home/amonoff/Projects/tracelock/internal/httpdir/response.go#L18-L20) — If `json.NewEncoder(w).Encode(v)` fails, you call `http.Error()`, but the status header was already written by `w.WriteHeader(status)` on line 16. This will log a `http: superfluous response.WriteHeader call` warning. Just log the error instead of trying to write another response.

### 27. Missing `X-Forwarded-For` header parsing for rate limiter

[ratelimit.go:93](file:///home/amonoff/Projects/tracelock/internal/httpdir/middleware/ratelimit.go#L93) — `X-Forwarded-For` can contain multiple IPs (`client, proxy1, proxy2`). You should split on comma and take the first one. Currently, the entire header value (including proxy chain) is used as the key, so the same client behind different proxy chains gets separate rate limits.
